## 2. Модель ролей

**Где настраивается:** `/settings/task-planner` → вкладка **Roles**. Админ отмечает, какие
**портальные роли** дают вид «Planner Admin», а какие — «Team Lead». Маппинг лежит в
`app_settings` под ключами `roles_admin` / `roles_team_lead` (jsonb-массив `role_id`).
Сами роли и пользователи заводятся только в Portal Settings — апка своего реестра не имеет
(правило 3). Слоты ролей объявлены в `appRegistry.ts` → `AppConfig.appRoles`, поэтому
вкладка Roles автоматически появится у любой другой апки, которой понадобятся свои виды.

Роль вычисляется на лету, нигде не хранится (`useTaskPlannerRole()`), по порядку:

| # | Условие | Роль | Кто это |
|---|---|---|---|
| 1 | админ портала (`useAuth().isAdmin`) | **`admin`** | Влад, Павел — всегда, независимо от настройки |
| 2 | роль юзера ∈ `roles_admin` (вкладка Roles) | **`admin`** | планировщик-диспетчер без прав админа портала |
| 3 | email юзера совпал с `tp_teams.email` | **`team_lead`** | бригадир/PM своей бригады |
| 4 | роль юзера ∈ `roles_team_lead` | **`team_lead`** | бригадир, которого нет в `tp_teams` (без привязки к бригаде) |
| 5 | остальные | **`none`** | **в апку не пускаем** — Access denied |

**Видов ровно два.** Доступ к апке в портале (`applications`) сам по себе вида не даёт: если
пользователю не назначен ни Planner Admin, ни Team Lead, `TaskPlannerLayout` показывает
Access denied вместо любого экрана планировщика. Гейт стоит на обёртке всех роутов
`/task-planner/*`, поэтому прямая ссылка его не обходит.

Реализация — два зеркальных слоя, гейт обязан быть на обоих:

- **UI**: `pages/task-planner/useTaskPlannerRole.ts` → `{ role, teamId, teamName }`.
  Ищет бригаду через `fetchTeamByEmail()` (узкий запрос по `tp_teams`, `ilike` = регистронезависимое равенство).
- **БД**: SQL-функция `public.tp_my_team_id()` (миграция `0006`, `security definer`) — тем же
  правилом (email ↔ `tp_teams.email`) скоупит RLS-политики.

Чтобы бригадир вообще попал в апку, ему нужно (обычным портальным путём, **не** внутри TP):
1. приглашение в **Portal Settings → Users** на рабочий Google-аккаунт;
2. роль, у которой в доступах есть Task Planner (`role_applications`);
3. эта же роль — отмечена в **App Settings → Roles → Team Lead** (либо его email есть в `tp_teams`).

## 5. Исполнение задачи — модель (решено 2026-08-13)

Источник: прототип Lovable **`crew-wise-ai`** (экраны `My Tasks`, `Task Details`,
`Task Completion Details`), показан заказчиком 2026-08-13.

### 5.1 Две независимые оси

Планирование и исполнение — **разные оси, не одно поле**. `scheduled` и «выполнена» не
взаимоисключающи: задача остаётся запланированной на дату и при этом может быть выполнена.

| Ось | Поле | Значения |
|---|---|---|
| **Планирование** (как есть) | `tp_tasks.status` | `requested → proposed → scheduled` (+ `archived`, объявлен в типах, в UI не используется) |
| **Исполнение** (новое) | `tp_tasks.execution_status` | `pending → completed → approved`, ветка `rework → pending` |

Ось исполнения живёт **только у `status = 'scheduled'`**: пока расписание не утверждено,
исполнять нечего. Дефолт при переходе в `scheduled` — `pending`.

| `execution_status` | Что значит | Кто ставит |
|---|---|---|
| `pending` | назначена, бригадир ещё не отмечал | система (дефолт) |
| `completed` | бригадир нажал **Complete** (+ `completed_at`, `completed_by`) | `team_lead` |
| `approved` | подтверждено сверху, задача закрыта | апрувер (см. 5.4) |
| `rework` | вернули бригадиру с комментарием; из `rework` задача снова доступна к Complete → `pending` | апрувер |

**`in_progress` не вводим** (решено 2026-08-13): кнопки «Start» у бригадира нет, а статус без
явного действия будет врать. Если заказчик потом попросит «вижу, что бригада выехала» —
добавляем кнопку Start и статус вместе, одним куском.

### 5.2 История манипуляций — `tp_task_events` (append-only)

Кнопка **info** в `Task Details` открывает `Task Completion Details → Recent History`. Это
**не поля в задаче**, а отдельная журнальная таблица — только так в одну ленту лягут и отметка
бригадира, и комментарий апрувера, и возврат на доработку.

```
tp_task_events (append-only, никогда не UPDATE/DELETE)
  id, task_id, actor_id, actor_role ('admin' | 'team_lead'),
  event_type ('completed' | 'approved' | 'rework' | 'note' | 'photo' | 'status_change'),
  from_value, to_value,   -- для смен статуса
  comment,                -- текст (комментарий апрувера / заметка)
  created_at
```
Окно «Recent History (Last 3 changes)» = последние N строк по `task_id`, свежие сверху.
Notes и фото из модалки — тоже события (`note` / `photo`); вложения — `tp_task_photos`
(`task_id`, `event_id`, `path` в бакете, `created_at`).

### 5.3 Экраны

- **`My Tasks`** (бригадир, прототип) — дата + переключатель `Yesterday / Today / Tomorrow`,
  список задач **своей бригады** со `status = 'scheduled'` на выбранный день, кнопка `Complete`
  на карточке. Клик по карточке → `Task Details`: `info` (история), `Notes` + `Add Note`,
  `Photos` + `Upload Photos`, `Complete`.
- **Approval-вью** (апрувер) — на прототипе его нет, но без него `completed` некуда девать:
  список задач в `completed`, действия `Approve` и `Send to rework` + комментарий.
  Комментарий при `rework` — обязателен.

### 5.4 Кто апрувит

**Пока — портальный админ** (`admin`), это временное решение на время разработки.
Финальную модель уточняем у Павла — см. §7.
